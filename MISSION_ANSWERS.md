# Mission Answers — Day 14

## Part 1: Localhost vs Production

### Exercise 1.1: Anti-patterns found

In `01-localhost-vs-production/develop/app.py`:

1. `OPENAI_API_KEY` is hardcoded. A real key committed to source control could be exposed.
2. `DATABASE_URL` includes hardcoded credentials and a machine-specific database address.
3. Configuration such as `DEBUG` and `MAX_TOKENS` is hardcoded rather than read from the environment.
4. `DEBUG` is always enabled, which is not an appropriate production default.
5. The app uses `print()` for diagnostics instead of structured logging.
6. It prints the API key, which would expose a real secret in application logs.
7. There is no health-check endpoint for a platform to check whether the app is alive.
8. Uvicorn binds to `localhost` and uses a fixed port, so it is not configured for container/cloud networking or an injected `PORT`.
9. `reload=True` enables development reload behavior when the app starts.
10. The app has no application-level startup/shutdown lifecycle or cleanup logic.

### Exercise 1.2: Run the basic version

Run from `01-localhost-vs-production/develop/`:

python app.py

In another terminal:

### Exercise 1.3: Compare basic and advanced

| Feature | Basic | Advanced | Why it matters |
|---|---|---|---|
| Configuration | Hardcoded values in `app.py` | `config.py` loads settings from environment variables and validates production configuration | The same image can be configured differently across environments without editing code or committing secrets. |
| Health and readiness | No health or readiness endpoint | `/health` reports liveness; `/ready` reports whether startup is complete | Platforms can restart an unhealthy process and avoid routing traffic to an app that is not ready. |
| Logging | `print()` statements, including the key | Python logger emits structured JSON events and logs request/response metadata without the key | Structured logs are easier to search and aggregate; excluding secrets prevents credential exposure. |
| Shutdown | No app-specific lifecycle or cleanup logic | FastAPI lifespan handles startup/shutdown and readiness state; a SIGTERM handler records termination while Uvicorn performs its graceful shutdown | Lifecycle hooks provide a place to initialize and clean up resources and help deployments stop without interrupting in-flight work. |
| Network and port | Binds to `localhost:8000` | Uses configurable host/port, defaulting to `0.0.0.0` and `PORT` | Containerized services must listen on an externally reachable interface and the port supplied by the platform. |
| Development mode | Reload is always enabled | Reload is tied to the `DEBUG` setting | Development conveniences should not be enabled unconditionally in production. |

## Part 2: Docker Containerization

### Exercise 2.1: Basic Dockerfile

1. **Base image:** `python:3.11`, the full Python image rather than the smaller `slim` variant.
2. **Working directory:** `/app`.
3. **Copy requirements first:** Docker caches each instruction as a layer. If application source changes but `requirements.txt` does not, Docker can reuse the dependency-install layer instead of reinstalling packages.
4. **`CMD` vs `ENTRYPOINT`:** `CMD` supplies the default command or arguments and is easy to replace when starting a container. `ENTRYPOINT` defines the executable; arguments supplied to `docker run` are passed to it. When combined, `CMD` commonly supplies default arguments to `ENTRYPOINT`.

### Exercise 2.2: Build and run the basic image

The basic image uses one stage: it installs Python dependencies, copies the app and shared mock utility, then starts the app with `python app.py`.

- **Develop image size (`docker images my-agent:develop`):** 1.67 GB (reported as 1667.8 MB by the image inspection used here).
- **Container test:** ran the container on host port 8001 and sent `POST /ask?question=Hello`; HTTP 200 with an `answer` field.

### Exercise 2.3: Multi-stage production image

- **Stage 1 (`builder`):** starts from `python:3.11-slim`, installs build tools (`gcc`, `libpq-dev`), then installs Python dependencies into `/root/.local`.
- **Stage 2 (`runtime`):** starts from a fresh `python:3.11-slim` image, creates a non-root `appuser`, copies the installed Python packages and runtime source, and configures the health check and Uvicorn command.
- **Why it is smaller:** the final stage does not include the builder's compiler and build dependencies; it contains only the runtime image, installed packages, and app files.
- **Advanced image size (`docker images my-agent:advanced`):** 240 MB (239.8 MB by image inspection).
- **Size reduction:** `(1667.8 - 239.8) / 1667.8 * 100% = 85.6%`.

### Exercise 2.4: Docker Compose stack

```text
Client
  |
  v
Nginx :80 (published on host port 80)
  |
  v
Agent :8000 (internal network)
  |                 |
  v                 v
Redis :6379       Qdrant :6333
  (internal network; no host ports published)
```

Compose declares the agent, Redis, Qdrant, and Nginx services on an internal bridge network. Nginx proxies HTTP requests to the agent; Redis and Qdrant are configured as internal dependencies and their URLs are passed to the agent. The current demo handler does not make Redis or Qdrant calls. The compose file does not set a replica count, so it starts one agent by default. Verified through Nginx: `GET /health` returned HTTP 200 and `POST /ask` with a JSON body returned HTTP 200.

## Part 4: API Security (CP3)

### Exercise 4.1: API key authentication

- The `/ask` route injects `verify_api_key` as a FastAPI dependency. It reads `X-API-Key` and compares it with `AGENT_API_KEY`.
- Missing key returns **401 Unauthorized**; a supplied but incorrect key returns **403 Forbidden**; the configured key returns **200 OK**.
- To rotate the key, update the `AGENT_API_KEY` environment variable in the deployment environment and restart/redeploy the service. Do not commit the key or print it in logs.
- Verified locally with `AGENT_API_KEY=secret-key-123`: missing `401`, wrong `403`, correct `200`.

### Exercise 4.2: JWT authentication

The client posts credentials to `POST /auth/token`. The app verifies the demo user, then signs an HS256 JWT containing the subject, role, issue time, and 60-minute expiry. Protected requests send it in `Authorization: Bearer <token>`; the dependency validates the signature and expiry before returning the user's identity and role. A missing token returns **401**. The token used for local testing is intentionally not recorded here.

### Exercise 4.3: Rate limiting

The limiter uses a **sliding window** of request timestamps stored in a deque for each user. The student/user tier permits 10 requests per 60 seconds; the admin tier permits 100 per 60 seconds. Requests over the tier limit return **429 Too Many Requests** and include `Retry-After`/rate-limit headers. Admins receive a higher quota; the limit is not removed.

Verified with the student account: no token `401`; valid token and requests 1–10 `200`; request 11 `429`.

### Exercise 4.4: Cost guard

The checked-in demo `CostGuard` tracks token usage in memory. It checks a **$1 per-user daily budget** and a **$10 global daily budget**, warns when a user reaches 80% of their budget, and records estimated input/output token costs after each request. It blocks a user over budget with **402** and blocks service when the global budget is exhausted with **503**. A local over-budget check returned `402`.

The exercise's suggested Redis solution is a separate production-oriented design: store spending per user and month in Redis so budget state survives process restarts and is shared across instances. It uses a $10 monthly limit, unlike this demo's in-memory daily budgets; the two should not be described as the same implementation.

## Part 5: Scaling & Reliability (CP4)

### Exercise 5.1: Health and readiness

- `GET /health` is a liveness check: it reports status, uptime, version, environment, and a memory check. The platform can restart the process if it is unhealthy.
- `GET /ready` is a readiness check: it returns **200** when startup has completed and the app can accept traffic, and **503** when it is not ready.
- Local verification: `/health` returned `200` with status `ok`; `/ready` returned `200` with `ready: true`; `POST /ask` returned `200`.

### Exercise 5.2: Graceful shutdown

The app's lifespan marks the service not ready during shutdown. Middleware tracks in-flight requests; Uvicorn handles `SIGTERM` and waits for active work, up to the configured 30-second timeout. Verified with a real server process: a request already in progress returned **200**, the server exited with code `0`, and the graceful-shutdown message was logged.

### Exercise 5.3: Stateless design

The production app stores session history as JSON in Redis under `session:<session_id>` with a one-hour TTL. Any agent replica can read and update that shared session. If Redis is unavailable, the demo falls back to a process-local dictionary; that fallback is not safe for multi-instance scaling because each replica has separate memory.

### Exercises 5.4–5.5: Load balancing and stateless test

The Compose stack contains three agent replicas, Redis, and Nginx. Nginx is published on host port `8080`, proxies to the agents, and Redis is shared by all replicas.

- All three agent containers and Redis became healthy.
- Through Nginx, `/health` and `/ready` returned **200**.
- `test_stateless.py` sent five turns; requests were served by three distinct instance IDs, while the shared session history contained all 10 user/assistant messages.
- This test script verifies cross-replica session persistence; it does not kill a replica. The K5 instructions correctly say the script does not stop an instance, so this run does not claim to verify failure failover.
